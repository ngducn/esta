# 01 Database: supabase/migrations, supabase/tests, supabase/seed

Reviewer 01. Snapshot `/tmp/esta-thermo-wt` at 5d19277. Read only. Nothing was run against a database.

## Verdict

This is the most disciplined part of the codebase I would expect to find in a two-person app, and it is also where the most expensive structural decision lives. Security-definer hygiene is close to flawless. The pgTAP suite tests behavior rather than restating the schema. Comments explain the reason for each rule. The problem is shape, not care. The rent planner, payment status, payment allocation, completeness facts, lease transitions and the national-ID detector are each written twice, once in SQL and once in `packages/core` TypeScript. Sampled parity tests hold them together, and the two have already drifted. Two "no overlap" invariants are enforced with hand-written locks and EXISTS checks where Postgres has a declarative constraint for exactly that job. The write lockdown for money tables is built by creating policies and then dropping them in seven files. And no file holds the current definition of anything that changed twice. I trust the data this produces today. The cost of changing it is roughly double what it should be.

## Ratings

- **Readability: 6/10.** The comments are unusually good at saying why, but the current body of `issue_invoices` lives in the third of three migrations, `property_list_rows` in the fifth of five, and the planners are 20-variable plpgsql loops (measured: 16 objects redefined, 786 superseded lines).
- **Quality: 7/10.** Every one of 116 functions pins `search_path = ''`, every public definer function is membership-guarded or service-role only, and the tests are behavioral, but money rules are duplicated across two languages with sampled parity, and two core invariants are procedural rather than declarative.
- **Performance: 7/10.** Foreign keys and access paths are indexed with care. Nothing here is slow at one household's scale. Three shapes would not scale: the per-row RLS function, the planner replaying every period from lease start each night, and an unindexable `ilike` on a computed view column.

## What fills the 18.5k lines

Measured with `wc -l supabase/migrations/*.sql`: 19,047 lines across 41 files. One generated file, `20261007006100_reference_data.sql`, accounts for 14,087 of them (74%). It holds admin units, the legacy commune map, bank BINs, land-use codes and tax rules. It carries SHA-256 hashes of its CSV inputs. Its generator refuses to rewrite an applied migration (`scripts/reference/build-migration.ts:149-154`) and emits a fresh migration for land-use changes (`:156-165`). That is the right home and the right discipline for reference data production needs. The other 4,960 lines are schema. Of those, 3,265 are function and view bodies, and 786 are bodies later superseded by `create or replace` in a later file (measured with an awk pass over `create (or replace) function|view` spans; superseded = total minus last definition per name).

## Findings, ranked

### 1. The billing rules exist twice, and the twins have already drifted (structural, missed code-judo)

`private.lease_periods` (`20261007306700_lease_changes.sql:102-179`) is a line-for-line port of `generateSchedule` (`packages/core/src/schedule/generate.ts:28-77`). It comes with SQL ports of `monthsUntil` and `scaleRoundHalfUp` (`20261007302000_leases.sql:295-317`) and of `planInvoices` (`20261007306700_lease_changes.sql:182-209`). The same pattern repeats for `private.payment_status` (`20261007304000_collections.sql:108-124`, twin of `derivePaymentStatus`), allocation inside `record_payment` (`20261007305000_record_payment.sql:94-106`, twin of `allocatePayment`), `property_completeness_facts`, the lease state machine in `guard_lease`, and the national-ID regex in `holds_national_id` (`20261007203000_document_extractions.sql:35-55`). The migrations reference `packages/core` twelve times to say which TypeScript function each mirrors (`rg -c packages/core supabase/migrations/*.sql`). Measured.

Parity is sampled, not proved. The preview parity test (`apps/web/src/server/actions/leases.integration.test.ts:151-191`) compares 18 lease shapes times 4 paid-through dates on a single as-of date with a 35-day horizon. None of its escalating cases reach their first step inside that horizon: the percent case starts 2026-08-10 every 12 months, and the fixed case starts 2026-10-16 every 6 months. Escalation parity rests on the cron test's six nights (`apps/web/src/server/cron/cron.integration.test.ts:159-230`). Measured.

They have already drifted. TypeScript `planInvoices` takes `CompletedReadings` and moves `issueOn` earlier for owner-metered units (`packages/core/src/lease/invoicing.ts:47-58`). The SQL planner does not ("without ... meter readings (P3-14)", `20261007302000_leases.sql:318-321`). The seed builds its invoices with the TypeScript planner and passes readings (`supabase/seed/generator/leasing.ts:166-171`). So the demo data contains issue dates the production SQL path cannot produce. Measured for the code paths. The size of the visible effect is inferred.

Why it matters: every billing rule change from now on (meter lines in P3-14, recurring charges, tax) is two implementations in two languages plus a harness that needs a live stack. The next engineer has to know that `invoicing.ts` is the spec but not the writer.

Remedy (the code-judo move): make SQL the single planner, because the writer has to be SQL. `public.preview_activation` already exposes the plan as an RPC (`20261007302000_leases.sql:447-470`), and `public.national_id_indexes` already applies this pattern ("The one judge of SPEC D11", `20261007305200_national_id_judge.sql:1-16`). Add one `public.lease_schedule(p_lease_id, p_until)`: a definer function guarded by `is_member` that returns `lease_periods` rows. `PeriodTimeline.tsx` is a server component, so it can read those rows. `tax/attribute.ts` already takes "a `generateSchedule` result", which is plain data, so the server can pass it SQL rows. The seed can insert leases and call `run_invoicing` per as-of date, which also fixes finding 6. That deletes `generate.ts`, `invoicing.ts`, `escalation.ts`, the schedule date and rounding twins, about 800 lines of their tests, and the parity harness. If the team keeps TypeScript as the spec, the minimum is to make parity exhaustive and stack-free. A fast-check generator in TypeScript would write cases and expected rows to a fixture that pgTAP replays, as `invoice_balances_parity.test.sql` already does with `fixtures/payment_status.csv`.

### 2. Overlap invariants are hand-rolled where an exclusion constraint deletes them (missed simplification, correctness)

The header of `20261007302000_leases.sql:1-4` promises "the invariants a bug in any caller must not break: ... one invoice per stretch of a lease". The table does not enforce that. `invoices` has only `unique (lease_id, period_start)` (`:74`). The overlap rule is an `EXISTS ... daterange && daterange` skip inside `private.issue_invoices`, and that loop is pasted into all three versions of the function (`20261007302000_leases.sql:422-425`, `20261007306200_invoice_cron.sql`, `20261007306700_lease_changes.sql:224-227`). The service role, the seed and any future meter-reading path can write overlapping invoices without the constraint noticing. For leases, `guard_lease` takes a row lock on the unit and then runs an EXISTS overlap query (`20261007306700_lease_changes.sql:87-97`). It raises errcode `23P01`, which is `exclusion_violation`, the exact code a real exclusion constraint would raise. Measured.

Remedy: `create extension btree_gist`. Then `alter table leases add constraint leases_no_overlap exclude using gist (unit_id with =, daterange(start_date, end_date, '[]') with &&) where (status in ('active', 'terminated'))`, and on invoices `exclude using gist (lease_id with =, daterange(period_start, period_end, '[]') with &&) where (status <> 'void')`. The unit lock, the race comment and the trigger's overlap branch go away. The invariant now holds for every writer. In `issue_invoices`, catch `23P01` in the existing exception block next to the memo-code retry and skip. Do not use a bare `on conflict do nothing`, because that would also swallow a memo-code collision. One semantic call has to be made explicitly: today a void invoice still blocks its stretch, because the EXISTS check has no status filter.

### 3. No file holds the current definition of anything (spaghetti across migrations, legibility)

`property_list_rows` is redefined in full five times (`20261007102000`, `201100`, `202000`, `202100`, `302000`). The latest copy carries the comment "Every Phase 1 column keeps its place" (`20261007302000_leases.sql:509-510`), which is the tax `create or replace view` levies on column order. `issue_invoices` exists in three copies, `set_property_location` in three, and `plan_invoices`, `guard_lease`, `run_invoicing`, `suggest_current_unit`, `claim_agent_job` and eight more in two each. Together that is 786 superseded lines. Measured. To read the invoice pipeline today you open `leases.sql`, `invoice_cron.sql` and `lease_changes.sql` and work out which definition won. Each new version also restates the full body. Two of them begin with a sentence of diff narration ("The 20261007302000 guard, with end_date free to move only ...", `20261007306700_lease_changes.sql:53`). That is the reader reconstructing a diff by hand.

Remedy: adopt Supabase declarative schemas. Put one file per function or view in `supabase/schemas/`, have `supabase db diff -f <name>` generate the migration, and let review read the schema file. If that is too large a step, have CI commit a `pg_dump --schema-only` snapshot and fail when it is stale, so the current state has one diffable home. Smaller note: the version prefixes are plan ordinals, not timestamps (`20261007306700` reads as hour 30, minute 67). The CLI's digits-only regex accepts them. Any tool that parses them as times will not.

### 4. The money write lockdown is expressed by subtraction, three ways, and part of it is unreachable (boundary, legibility)

`private.enable_household_rls` always creates select, insert, update and delete policies (`20261007000100_tenancy.sql:139-170`). Its 23 call sites produce 92 policies. Thirty-three of them are dropped right after creation in seven files: `agent_core` drops 8, `leases` 7, `collections` 6, `document_extractions` 5, and four other files drop the rest. On top of that come 11 `revoke insert/update/delete ... from authenticated` statements, column-level `grant update (...)`, and 11 trigger branches keyed on `current_user = 'authenticated'`. Measured with `rg -c`. Four mechanisms express one intent: "sessions read; only definer functions write". Some of the layers are now dead. `20261007306700_lease_changes.sql:47-51` grants update only on columns that exclude `status`, so Postgres refuses a member's status write with a generic `42501 permission denied` before `guard_lease` runs. The pgTAP test expects exactly that message (`supabase/tests/leases.test.sql:48-50`). No test anywhere asserts `ESTA_LEASE_ACTIVATE_THROUGH_FUNCTION` or `ESTA_LEASE_STATUS_THROUGH_FUNCTION` (`rg THROUGH_FUNCTION` outside migrations returns nothing). The UPDATE branch at `20261007306700_lease_changes.sql:65-69` is unreachable for the only role it targets. Inferred from privilege-check ordering plus the test's expected message. Not executed.

Remedy: make write mode a parameter of the recipe. For example, `enable_household_rls(table, writes => 'definer_only' | 'member' | 'admin')`, where `definer_only` creates only the select policy and revokes writes from `authenticated` in one place. The call site then states the invariant. The 33 drops and most of the revokes disappear. A catalog test in the style of `policy_functions.test.sql` can assert each table's mode. Delete the unreachable trigger branch, or keep it and say in one comment that it is a backstop.

### 5. The lease escalation boundary is looser than the amendment boundary next to it (type and boundary)

`leases.escalation` is jsonb, and its check validates only `kind` (`20261007302000_leases.sql:21-23`). `lease_amendments.changes` gets an exact shape check: allowed keys, types, ranges and the cycle set (`20261007306700_lease_changes.sql:11-21`). Members hold the update grant on `escalation` for drafts (`:48-50`). `{"kind":"percent","value":500}` without `every_months` reaches `for i in 1 .. null` in `lease_periods` and raises "upper bound of FOR loop cannot be null". `every_months: 0` raises `division_by_zero`. Both appear as raw Postgres errors at activation instead of `ESTA_*` codes. Money is never written wrong, because activation fails first. Inferred from reading. Not executed. Remedy: four typed columns with checks (`escalation_kind`, `escalation_every_months`, `escalation_value`, `escalation_rounding_vnd`), or one jsonb check that mirrors the amendment check. Typed columns also remove the `->>` casts in both planners.

### 6. Three models of "what the nightly job writes" (modularity)

SQL `issue_invoices` skips any stretch that overlaps an existing invoice and never rewrites one. The seed (`supabase/seed/generator/leasing.ts:162-171`) plans month by month and overwrites by period start (`byStart.set`), then applies one final plan with readings. `cron.integration.test.ts:141-155` models it a third way: nightly, skip on overlap. When a plan changes between months, the seed can hold rows that the cron would never have written. The north-star e2e runs on that seed. Measured for the code. The effect on current seed rows is unverified. Remedy: covered by finding 1. The seed calls `run_invoicing` per as-of date, and the test's `nightly()` helper goes away.

### 7. Performance shapes to watch, not to fix now

Every generated policy calls `private.is_member(household_id, ...)` per row (`20261007000100_tenancy.sql:102-116, 149-150`). It is a `security definer` SQL function, so Postgres cannot inline it, and each row costs an EXISTS on `household_members`. This is fine for one household. On `audit_log`, which gains a row for every audited write, it is the first thing that grows. The standard fix is a policy of `household_id = any (select private.my_household_ids('viewer'))`, which runs once as an initPlan. `lease_periods` replays every period from lease start on every nightly run and compounds escalation in a nested loop (`20261007306700_lease_changes.sql:136-170`). That is O(periods × steps) per lease per night, which is trivial for 10-year leases. `property_list_rows` recomputes `esta_unaccent` plus `regexp_replace` over a lateral legacy-map aggregate for every row. `server/properties/list.ts:97` then filters that computed column with `ilike '%token%'`, which no index can serve. A stored generated `search_text` with a trigram index is the fix if the list ever grows. The detail page also reads this view for one property (`server/properties/detail.ts`). Indexes cover the FK and access paths I checked: `payment_allocations_invoice_idx`, `invoices_issue_idx`, `admin_unit_legacy_map_new_commune_code`, and the ownership and units composites. The cron loops households in TypeScript, one RPC each (`apps/web/src/server/cron/invoices.ts:16-17`), while `end_expired_leases` covers all households in one call. The inconsistency is harmless with N = 1.

## What is genuinely good

Definer discipline is the best I have seen in a codebase this size. `set search_path = ''` appears on 116 of 116 functions. Every function carries an explicit `revoke all ... from public` and a narrow grant (158 grant or revoke statements). Of the 17 public security-definer functions, 14 check membership in the body. The rest (`run_invoicing`, `end_expired_leases`) are executable only by `service_role` (measured by an awk scan of definer bodies). Composite `(household_id, id)` foreign keys make a cross-household reference structurally impossible. The pgTAP suite proves behavior: 308 `throws_ok`, 307 `ok`, 176 `is`, 140 `results_eq`, 107 `lives_ok`, 95 `is_empty`, 70 `tests.sees_household`, and only one `has_index` plus one `col_type_is`. Scenario fixtures such as `issued_snapshot` in `lease_changes.test.sql` prove issued invoices stay byte-identical through amend, terminate and renew. Lessons are encoded as catalog tests rather than prose. `policy_functions.test.sql` fails when any policy calls a function its role cannot execute, and `pnpm db:test` fails on a table without RLS or a test file. Money is `bigint` with range checks everywhere, idempotency keys are unique constraints, and the seed's SQL emitter (`supabase/seed/generator/sql.ts`, 64 lines) is small, typed and deterministic.
