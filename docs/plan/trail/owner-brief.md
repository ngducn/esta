# Owner brief, shared by every PR owner

You own one PR of Esta v1 from build to merge-ready. You never merge, never arm auto-merge, never close a PR, never force-push a branch other than your own, and never touch topology beyond your own branch. The root owns topology and merges.

## Read first, and only this (2026-11-02, lean for usage)

Everything you read stays in your context and is paid for again on every later turn, so read narrowly.

1. Your brief, then this file. `CLAUDE.md` is already in your context; do not read it again. Do not load `poteto-mode`, its playbooks, `standing-orders.md` or the thermo-nuclear skill: this file is your process and the reviewers cover code quality.
2. The files your brief names, and the code you change. Find with `rg -n` or `git grep -n`, then read line ranges (`sed -n 'a,bp'`). Never `cat` a whole spec, design doc, `preview.html` or the plan; never print a whole JSON message file (read keys with `jq`). Pipe long command output through `tail -40` or `rg` for the failing lines.
3. Spec sections only where your brief points: `docs/spec/DOMAIN-VN.md` for money, addresses, certificates or tax; `ARCHITECTURE.md` for the one home of a parser, result type, server action, toast or test helper; `.claude/skills/impeccable/reference/craft-floor.md` for UI. Skip `/impeccable shape` when a finished design exists for the screen.

## Lifecycle

0. `gh issue list --state open --search "<pr id lowercase> in:title"`: every open issue tagged with your PR id is in scope; close it from your PR with `Closes #<n>` and a red test.
1. Work in the worktree and branch the brief gives, with the `ESTA_SLOT` it names.
2. Push early and open the PR ready (never draft) with a Conventional Commits title, the PR id as scope, and the tier on the body's first line.
3. Name the data shape first. Build. Push after every verifiable unit.
3a. Codify (Ryan, 2026-11-06). Every defect you fix, including one you cause and catch while building, ships with the check that would catch it next time (CLAUDE.md "Codify every finding"). The PR body has a `## Codified` section listing each defect and its check, or `None found`; root's merge script refuses a PR without it. Your diff raises no `pnpm quality` metric and adds no second way to do something ARCHITECTURE.md gives a home.
4. Prove it on the real surface per the tier table in `verification-tiers.md`: `pnpm check`, the specs your change touches, and the screenshots your tier asks for (two to four, through the verify skill). Evidence under `/tmp/owner-<pr id>/`.
5. Run `/deslop`. Run `/no-comments` only when the diff adds comment lines (`git diff origin/main... | rg '^\+.*(//|/\*)'`), because it starts a whole subagent. Then `pnpm check` on the committed head. Push.
6. Wait for CI with `~/.claude/orchestrate/esta/bin/wait-ci.sh <n> <full head sha>` in the foreground with a 600000 ms Bash timeout: exit 0 is green, 1 is red or a moved head, 3 is still running, so run it again. Never background a CI watch and never poll by hand: background watchers outlived their agents three times on 2026-11-06. Fix a red job that your change causes.
7. Report once, only after the final `ci` result at your pushed head (`gh pr view <n> --json headRefOid,statusCheckRollup`; an earlier head's green run does not count, and root's merge script reads the same), with no background job of yours still running: each one wakes you and makes you report again, which costs tokens. Report code-ready to the root (SendMessage to `main`, at most 10 lines): PR URL, head SHA, `ci` state, evidence, what you could not check and why. Then stop: do not wait for the review. A fresh agent takes any fix round.

## Rules

- Evidence budget (2026-11-02): two to four key screenshots in the PR body, no videos or full screenshot matrices; Lighthouse only when the change touches a route's loading path (images, fonts, the JavaScript bundle), three runs per side; run only the specs your change touches. These override any older brief or plan box that asks for more.

- CI runs on GitHub Actions for every PR push: the `ci` check, about 11 minutes, shown by `gh pr checks <n>`. The merge gate is a green `ci` at the exact head. Run `pnpm check`, a production build or any Playwright run through `~/.claude/orchestrate/esta/bin/heavy.sh <command>`. When Actions is down, the fallback is `/Users/ngducn/Workplace/esta/tools/ci-local.sh <worktree> <pr> <slot>`, once at code-ready, never in a loop.
- Screenshots in a PR body or comment must render on GitHub. Publish them with `~/.claude/orchestrate/esta/bin/pr-media.sh <pr> <image>...` (it pushes them to the `pr-media` branch) and paste the Markdown it prints. Never list `/tmp` paths as evidence a reviewer is meant to see.
- Write temporary files (PR bodies, logs, probes) under `/tmp/owner-<pr id>/`, never in a shared scratchpad, so parallel owners never overwrite each other.
- Name every new migration `supabase/migrations/20261007<P><NN><S>00_<name>.sql`, where `<P>` is the phase digit, `<NN>` the PR's two-digit `Seq` in `docs/plan/trail/pr-inventory.md` (its delivery position in the phase, not its id number) and `<S>` a sequence digit within the PR. For example P1-07, Seq 06, names its first migration `20261007106000_...` and its second `20261007106100_...`. In Phase 0, `Seq` equals the id number, so merged migrations keep their versions. Versions must increase in delivery order. Before your verdict, check that your versions sort after the newest migration on `main`; if a PR with a later `Seq` merged first, renumber yours to the next free version after it and say so in the PR body. This rule overrides the placeholder timestamps in the plan's Files boxes. P0-02 keeps its existing `0001xx` to `0004xx` versions.
- Before starting a Supabase stack on your slot, run `~/.claude/orchestrate/esta/bin/slot-free.sh <slot>`; start only when it exits 0. It also refuses a slot that root CI holds while its first jobs run without a stack.
- Heavy jobs share the machine under one lock (Ryan, 2026-11-01). Wrap every Playwright run (`pnpm e2e ...`), every Lighthouse run and every production build in `~/.claude/orchestrate/esta/bin/heavy.sh <command>`, which waits for the lock root CI also holds. Two Playwright runs narrowed to named spec files (`pnpm e2e e2e/x.spec.ts`) may share the machine; a full suite, `e2e:northstar`, a build, Lighthouse or a wrapper script runs alone, so call heavy.sh once per narrowed run, not around a script. Locally, run only the specs your change touches; the full suite runs in CI on every push and CI is the merge gate. Run the full suite locally only when GitHub Actions is down. If a test fails beside another run and passes alone, report it and `touch /tmp/ci-local/one-at-a-time`, which makes every job run alone again (concurrent runs swapped this machine on 2026-10-18).
- Never prune or remove shared Docker resources (`docker system|image|builder|volume prune`, other projects' images or volumes). If the Docker disk fills, stop and report to the root, who asks the operator.
- Many agents share this machine. Stop only processes you started, by the PID you recorded when you started them (`kill <pid>`). Never use `pkill`, `killall` or `kill` by name or pattern, which kills other agents' servers.
- Docker has 8 GB shared with another project's containers (`ekh-*`, never touch them), and each local Supabase stack takes about 1 GB. Run at most the one stack your brief names, stop it with `ESTA_SLOT=<slot> pnpm db:stop` when you are not actively testing, and never stop a slot you did not start. Port 3000 is taken; never use it.
- Real family data, `.env*` files, tokens and `fixtures-private/` never enter a commit, screenshot, log or PR body. Seed data names contain "Demo". Never print `apps/agent/.env.local`.
- Never create or change a cloud project, deploy, send real email, add a paid service or a new external data source. Stop and report instead.
- Money is integer VND. No `new Date()` in domain code. No `any`. Every user-facing string goes through next-intl. Design tokens only.
- Keep comments to a non-obvious why. No phase-narrating comments.
- If the plan section is wrong or impossible as written, do the smallest correct thing, record why in decisions.tsv and in the PR body under Tradeoffs, and tell the root.
- Known defect classes (2026-10-30). Reviewers found each of these more than once in Phase 5, always after the build. Check every one that your diff touches before you report code-ready, and say in the PR body how you checked it. Q-16 in `docs/plan/quality-2026-11.md` turns each into a check; once a class has its check, this list names the check instead:
  1. **A private row with a public copy.** Check: `tests.hidden_everywhere(table, row_id, reader)` in `supabase/tests/_harness.psql` proves the row, its `audit_log` history and every copy in `tests.content_copies()` are hidden from the reader; add a new copy there. `pnpm db:test` fails when a table with a narrower-than-household select policy has no test calling it (`scripts/table-coverage.ts`).
  2. **Count, then write.** Check: `twoAtOnce(call)` in `apps/web/src/test/two-at-once.ts` runs two calls together and returns both outcomes; use it in the test of every cap, limit or one-at-a-time rule. `pnpm db:test` fails on a new definer function that counts and inserts without `pg_advisory_xact_lock` (`scripts/count-then-write.ts`, baseline `quality/count-then-write.json`).
  3. **Clock edges.** Check: `clockEdges()` in `packages/core/src/clock/edges.ts` yields 23:59 and 00:01 +07, Sunday to Monday, month end and the frozen clock; run every day-, week- or month-keyed test over it, as `plan-jobs.test.ts` does. Review checks the helper is used.
  4. **Hidden pages.** A page a member may not see answers a real 404, with the same body as a missing page, never a 200 that says "not found". Not yet a check: the access table (Q-08) will generate a 404 test for every guarded route; until then prove it in your own e2e.
  5. **The number guard.** Check: `packages/core/src/guard/compounds.property.test.ts` tries a real number word beside every compound in `words.ts`, so a new compound is covered by adding it to the table; when a word can be a real count, the number rule wins and the prompt rewords.
  6. **Copied fixtures.** Extend an existing fixture or recording file rather than copying it, and keep generated JSON out of a new file when a shared one exists.
  7. **A class with no token.** Check: `pnpm classes:check` (`scripts/check-tailwind-classes.ts`, part of `pnpm check`) asks Tailwind whether every class in a `className`, `cn(...)` or `clsx(...)` produces CSS, so read the computed style only for what it cannot see (a class built from a variable).
  8. **A figure with two definitions.** A screen's total comes from the home the brief names, and a test compares it with an independent figure (another screen, or the database), never with itself. No mechanical check can catch this class: only a reader knows that two figures mean the same thing, so it stays on the review checklist in `verification-tiers.md`.
- Size (2026-10-19): keep a PR to one user outcome and its product code (everything except tests, migrations' pgTAP, generated types, seed and message files) under about 800 added lines. When the product code will pass that, stop and propose a split by user outcome to the root before building further. Tests have no cap.
